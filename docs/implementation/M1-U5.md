# M1-U5 — Clarification Generator

## Status

`COMMITTED`

The human explicitly approved this plan in the request to implement M1-U5. The unit moved from `PLANNING` through `PLAN_APPROVED` to `IMPLEMENTING`.

## Objective

Turn deterministic missing Brief readiness fields into a small set of concise questions. Save the user's answers together through the existing Brief editing workflow, recalculate readiness, and retain manual editing as a fallback.

## Dependencies and current state

M1-U2 deterministic readiness, M1-U3 structured AI and AIRun patterns, and M1-U4 Brief API/editing UI are `COMMITTED`. The working tree was clean before this planning documentation change. The approved Technical Architecture revision adds only `POST /projects/{id}/brief/clarifications` for generation; answers use the existing `PATCH /projects/{id}/brief` boundary.

## Approved scope and implementation plan

1. Add a strict, bounded `ClarificationSet` with 1–5 questions. Each item contains `field_key`, `question`, and `reason`; question and reason are non-empty after trimming and at most 200 characters. A versioned prompt receives the current saved Brief and the first five unresolved readiness fields in their deterministic order. It asks for one question per supplied field, uses known Brief facts as context, and does not let the model decide which fields are mandatory. Target price remains optional.
2. Hard post-schema validation checks only deterministic invariants: every returned `field_key` belongs to the unresolved subset supplied to the model, keys are unique, the returned set exactly covers that subset, and question/reason strings meet the stated structural bounds. Clarity, conciseness, redundant-question rate, and irrelevant-question rate belong in evals, not structured-output failure handling.
3. Reuse the shared structured AI client, one repair retry, and one `AIRun` with a distinct clarification operation and prompt version. If the shared runner needs post-schema validation, add a minimal optional hook while preserving M1-U3 Brief Interpreter retry and tracing semantics. Exhausted validation or provider failure leaves Brief data unchanged and exposes retry and manual-edit recovery.
4. Add session-scoped `POST /projects/{id}/brief/clarifications`. It takes no answer data and returns `{brief_revision, questions}` from a saved, incomplete Brief. Empty or already complete Briefs make no model call. After generation, recheck the source revision; reject a result made stale by an intervening edit. Generation never writes Brief or Requirement state. Questions are transient; `AIRun` uses existing persistence.
5. Persist answers only through the existing complete-snapshot `PATCH /projects/{id}/brief`. Add optional, nonnegative `expected_brief_revision` solely as an optimistic-concurrency guard. Check it before mutation under the existing workflow lock and return the existing Brief conflict response on mismatch. When omitted, preserve all M1-U4 PATCH behavior. Do not create another answer endpoint or duplicate Brief mutation logic.
6. In the Brief editor, offer on-demand generation for saved incomplete Briefs. Require other unsaved edits to be saved before generation or answer submission. Show controls for the currently supported readiness keys: core text, positive quantity, delivery date or period, material, and yes/no custom branding. Merge answers into the existing editable snapshot, creating only existing requirement kinds with importance left unset when unknown. Save all answers together by PATCH with the generation revision, then replace the displayed Brief and missing-field list with the response. Keep draft answers on validation or stale-revision errors; allow retry and manual editing.

## Acceptance criteria

- Deterministic readiness alone selects fields for clarification; the model only phrases questions for the supplied subset.
- Every generated question passes the exact field-key and structural checks. Subjective wording quality is measured by evals.
- Generation returns its source revision without mutating Brief content. A stale generation or answer save cannot overwrite a newer Brief.
- Answers save atomically through PATCH, preserve unrelated content, recalculate readiness, and advance revision once for a meaningful edit.
- Legacy PATCH callers without `expected_brief_revision` retain M1-U4 behavior; manual editing remains usable after AI failure.

## Tests and evals

- Contract and mocked-model tests: bounded schema, non-empty strings, unknown/duplicate/omitted keys, exact coverage, one repair retry, exhausted failure, and AIRun metadata. Add regression coverage proving the optional runner hook does not change Brief Interpreter retry or tracing behavior.
- API/integration tests: session isolation; no model call for empty or complete Brief; no Brief/Requirement write from generation; stale generation; PATCH revision mismatch checked before mutation; atomic mixed-answer validation; existing material and custom-branding mapping; preservation of known content; readiness and revision/no-op behavior; and legacy PATCH requests omitting `expected_brief_revision`.
- Initial version-controlled clarification evals: missing-field coverage, known-field redundancy, irrelevant-question rate, clarity, and conciseness, including category-specific requirements and optional target price. Follow the existing deterministic scoring and opt-in live-eval pattern.
- Frontend tests: generation and loading, save-together answers, stale state, validation feedback, AI retry, draft preservation, and manual fallback. Run backend and frontend tests, evals, Ruff, Pyright, lint, type checks, and build.

## Browser QA requirement

Browser QA is required because this unit changes the Brief workflow and frontend/backend interaction. In the later QA stage, exercise incomplete saved Brief → generated questions → saved answers → recalculated readiness → reload, plus stale/error recovery and manual editing. Record provider limitations accurately if live generation cannot be verified. Do not perform Browser QA during planning or implementation.

## Risks and explicitly out of scope

Stale questions, unsaved draft edits, model failure, and answer mapping to category-specific requirements are the main risks. Revision checks, saved-state generation, existing validation, atomic PATCH, and manual editing address them. No migration, new dependency, new readiness field or requirement kind, clarification-answer endpoint, framework, agent, infrastructure, Brief approval, post-approval behavior, supplier work, M1-U6 implementation, Review, Browser QA, Done Check, or commit belongs to this planning phase.
