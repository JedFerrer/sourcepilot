## Approved implementation plan

### 1. Explain empty supplier discovery

- In `SupplierReview`, use the existing discovery response to identify a successful empty result. Show: “No supplier candidates were found in the curated dataset for this Brief. Review the product category and requirements, then discover suppliers again.” Link “Review Brief” to the existing `#brief-complete` editor; retain the discovery action.
- The return-to-Brief action is navigation only. All edits, revision increments, approval invalidation/reapproval and supplier-staleness checks must follow the existing Brief workflow. Do not bypass approval to rediscover or clear stale evaluations through navigation.
  Existing M1-U6 behavior is preserved: a meaningful edit that remains complete retains approval and its timestamp; an incomplete edit revokes approval and requires explicit approval after completion. Both advance the Brief revision and retain existing downstream staleness rules. This unit does not introduce unconditional reapproval.
- Keep the outcome local to the current project, Brief revision and refresh context. Clear it when those change, a new discovery starts, or a non-empty result arrives. Do not introduce persistent discovery-history state or an API field.
- Initial/reloaded empty lists use neutral wording (“No supplier candidates to review yet”) with discovery/Brief guidance, without claiming that discovery ran. Read/request failures remain errors and must not be presented as successful empty discovery.
- Do not label an empty catalog result as proof that all suppliers fail requirements. Keep existing near matches and their requirement findings visible. Do not fabricate candidates, change filtering, or encourage weakening required requirements.

### 2. Make failed quote-status reads recoverable

- The processing poll currently swallows every rejected GET in `QuoteReview`. A repeated read failure therefore leaves “Processing PDF quote…” indefinitely, even if the server has completed or become stale.
- Add a per-quote status-read warning on a failed poll: “We couldn't check this quote's processing status. The last known status is shown. Try checking again.” Offer “Retry status check,” which reads the existing quote GET endpoint only.
- Retry only that read-only status request through the existing authorized API path. It must not restart extraction, create or increment processing attempts, modify persisted quote data, or bypass session/project ownership checks. Preserve the existing manual-entry fallback when the server reports an eligible state; a later explicit processing retry or manual save remains a separate user action.
- Keep the normal polling cadence and existing cancellation protection. Clear the warning after a successful read; show returned FAILED, STALE_PROCESSING or NEEDS_REVIEW through existing card behavior. Clear obsolete warnings on project change, quote removal or leaving processing.
- Keep the last quote data and unrelated quote edits usable. A status-read failure must not mark the quote FAILED/STALE locally, call processing retry automatically, upload again, or enable confirmation/manual fallback for a still-processing quote.
- Disable the explicit status-check action while its read is pending. Ignore late results/errors after deactivation or a changed quote/project context; an older failed read must not replace newer successful status feedback.
