## Objective

Make the persisted deterministic comparison understandable in the project workspace, including requirement outcomes, commercial facts, warnings, source provenance, and clear recovery when its inputs change.

## Dependencies and current state

- M4-U3 is committed. `GET /projects/{id}/comparison` returns the latest snapshot or `COMPARISON_NOT_FOUND`; `POST /projects/{id}/comparison/generate` creates a new snapshot or rejects ineligible inputs. Responses include `comparison_payload`, `generated_at`, and effective `stale` status.
- The payload contains the approved brief, supplier names and IDs, confirmed quote fields and origins, resolved facts with source references and context, requirement evaluations, typed warnings, and per-field completeness. The API remains the authority for evaluation and stale state.
- The workspace renders Brief, Suppliers, and Quotes. Comparison and Decision are presentation-only unavailable stages. Quote saves and confirmations reload QuoteReview locally; they do not notify the workspace. Brief and shortlist changes already notify the workspace.
- No comparison frontend, comparison tests, or browser automation suite existed at planning time.

## Proposed implementation plan

1. Add a typed frontend contract for the existing comparison response and its nested factual data at the UI boundary. Use the shared API client. Keep business evaluations, source precedence, generation eligibility, and staleness calculations on the backend; frontend helpers only format and label returned values. GET/POST remain authoritative.
2. Add a focused Comparison component to the project workspace. On load, distinguish no snapshot, loading, current, stale, and recoverable API error states. Offer generation or regeneration as a user action; frontend state only controls presentation and affordances. Show the server's eligibility message when generation is rejected. Do not duplicate backend eligibility rules or imply that a draft, unshortlisted quote, or single confirmed quote is comparable.
3. Render an accessible supplier-column comparison table with readable commercial rows (including unit price with currency, quoted quantity, MOQ, lead time, delivery, tooling, and shipping where present). Show Unknown and Conflict explicitly. Surface mixed currencies and quantity mismatch next to price/quantity, with wording that avoids an unsupported direct price ranking or currency conversion. Do not add a score.
4. Render each approved requirement with its importance and per-supplier `Meets`, `Does Not Meet`, `Unknown`, or `Conflict` result. Keep informational requirements visibly contextual. Emphasize required failures without hiding the supplier. Include completeness and typed warnings so missing or conflicting inputs are visible even when no requirement targets that field.
5. Add compact, inspectable provenance details for each displayed selected fact and requirement result: confirmed quote versus general supplier context, source references, quote value origin, supporting/provenance evidence IDs, and available supplier evidence labels or document page/block references. Show a user-corrected quote value as current while retaining its original PDF/extracted value and evidence as provenance only; never imply the original evidence supports the correction. Keep contextual general facts distinguishable from the selected confirmed quote. Reuse existing quote review for full document evidence; do not add PDF APIs.
6. Show a prominent outdated-state notice when `stale` is true while leaving the prior factual snapshot visibly marked as outdated. Offer `Regenerate Comparison` and explain when renewed Brief or shortlist approval is required. Make no AI commentary or suggested supplier look current; this unit adds neither capability.
7. Wire successful quote saves and confirmations, plus existing Brief and shortlist changes, to refresh comparison status in the workspace. Avoid polling or optimistic stale calculations. Keep Comparison discoverable in the five-stage shell without claiming frontend-calculated eligibility; leave Decision unavailable. Add responsive table overflow and clear focus/error states using current styling conventions.

## Acceptance criteria

- A user with at least two shortlisted, confirmed quotes can generate and understand a factual comparison without AI output.
- Supplier facts, prices and currencies, requirement states and importance, required failures, warnings, Unknown/Conflict, and available provenance are inspectable.
- Fewer than two eligible quotes, no snapshot, failed requests, and rejected generation have clear recovery paths.
- A changed confirmed quote or Brief shows an obvious stale notice; the prior snapshot is clearly outdated; regeneration displays a current snapshot using new values. Revoked shortlist approval is handled without suggesting generation will succeed until reapproval.
- Quote changes made on the open workspace refresh comparison status. No numeric score, FX conversion, analysis, or suggested supplier is introduced.

## Risks and decisions to verify during implementation

- The payload is a stored JSON snapshot rather than a purpose-built display DTO. Verify actual nested shapes and nullable values against M4-U3 tests before writing renderers; avoid UI assumptions about every quote field being present.
- The project stage remains `QUOTES` while Comparison is available. The shell should present Comparison as an available view within the existing workflow rather than claiming the backend has a new `COMPARISON` stage.
- A stale snapshot may be readable when generation is temporarily ineligible because shortlist approval was revoked. Keep it marked outdated and show the backend's reapproval message on regeneration attempts.

- New evaluator rules, source-precedence rules, quote revision semantics, schema migrations, comparison scoring, and currency conversion.
- New PDF viewing endpoints, supplier research, or unrelated frontend restructuring.
