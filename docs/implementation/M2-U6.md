## Objective

supplier through the bounded, read-only Sourcing Analyst.

## Approved implementation plan

1. Extend the M0-U5 AI client/provider boundary for Responses tool calls. Use an
   application-owned analyst loop with configurable defaults of four model turns
   and six successful tool calls. Every provider invocation, including repair,
   consumes one model turn; reuse the M2-U5 successful-call counter. The runtime
   limits may be configured with `SOURCEPILOT_ANALYST_MAX_MODEL_TURNS` and
   `SOURCEPILOT_ANALYST_MAX_TOOL_CALLS`.
2. Expose only the M2-U5 supplier snapshot and evidence tools. Persist minimal,
   ordered, M2-U6-specific AIRun steps, with `FAILED_LIMIT_REACHED` only when a
   runtime limit prevents completion.
3. Validate the typed explanation against the requested supplier, deterministic
   evaluation states, and evidence IDs. Revalidate session, project, candidate,
   and revision after the run before returning a result.
4. Add a synchronous, session-scoped per-supplier explanation endpoint returning
   explanation and `run_id`. Generate on demand without saving explanation text.
5. Add a supplier-review action showing explanation, cited evidence, loading,
   retry, and stale-state behavior. Internal run steps remain developer-facing.

## Explicitly out of scope

M2-U7 fixture expansion and shortlist approval, quote/comparison tools, a general
tracing framework, a parallel AI client abstraction, and new dependencies.

## Acceptance criteria

- Explanations agree with deterministic states and preserve required failures,
  Unknown, and Conflict.
- Cited evidence IDs belong to the permitted supplier and were returned by the
  evidence tool; unsupported output is rejected.
- Limits, provider/validation failure, and stale or changed authorization yield
  recoverable failures and no explanation.
- AIRun and ordered steps are persisted; the normal supplier UI does not expose
  internal model or tool traces.

## Tests and evals

Loop and limit tests; contract and groundedness evals; API scope/staleness tests,
including authorization changing during a run; frontend interaction tests;
backend and frontend checks; Browser QA during its own phase.

- **P1 — requirement state in model prose:** Requirement-backed model points now
  select a requirement and evidence IDs with `text: null`. Validation rejects

  requirement label and Meets / Does Not Meet / Unknown / Conflict state from
  the deterministic snapshot. Evidence-only concerns retain their supported
