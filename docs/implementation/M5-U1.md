## Persistence and API

- Add nullable `Project.preferred_supplier_id` and `Project.decision_notes` through migration `0015_preferred_supplier`, following `0014_comparisons`. Existing projects receive null values.
- Reference the supplier catalog with a named foreign key restricting supplier deletion. Do not add a decision-history table or a circular project-candidate foreign key.
- Return nullable `preferred_supplier_id`, derived `preferred_supplier_name`, and `decision_notes` consistently from project create/read/list/rename and decision responses. Load names without a supplier query per dashboard project.
- Add `PUT /projects/{project_id}/preferred-supplier`, returning the updated project with HTTP 200. Require `supplier_id: UUID | null`; accept optional nullable `decision_notes`, limited to 10,000 characters. Reject extra fields.
- Omitted notes preserve existing notes. Explicit null or blank notes clear them; trim nonblank notes. Clearing the preference preserves notes unless the request explicitly changes them.
- Reuse existing session ownership, transaction, and error conventions: 401 for missing/expired session, 404 for missing/foreign project, 422 for invalid input, and 409 `PREFERRED_SUPPLIER_NOT_SHORTLISTED` for an invalid new selection. Rejections leave both decision fields unchanged.

## Decision rules and UI

Resolve ownership, lock and reload the project using the existing project-lock convention, then apply these rules in order:

| Submitted supplier ID | Behavior |
|---|---|
| Null | Clear unconditionally; apply submitted notes semantics. |
| Equals the currently stored preferred supplier ID | Retain the choice and allow notes editing, even if the supplier has left the shortlist or candidate set. |
| Different non-null ID | Require current membership in this project's shortlist before updating either field. |

The equality check uses the persisted value read under the lock, not the client's remembered choice. Refresh membership before validating a different supplier.

**Existing M2 invariant:** supported supplier mutations clear `dismissed` when shortlisting and clear `shortlisted` when dismissing. Existing tests cover dismissal removing shortlist membership. This is an application invariant, not a database constraint. M5-U1 adds no independent `dismissed` eligibility rule: validation and option filtering use current project shortlist membership.

Any currently shortlisted supplier can be newly selected regardless of AI suggestion, required failures, Unknown/Conflict results, confirmed quote availability, or comparison participation. No stage or snapshot gate is added.

Add a focused Decision panel after Comparison:

- Show the saved supplier or **No Decision Yet**, an explicit supplier selector, optional notes, **Mark as Preferred Supplier**, **Save decision notes**, and **Clear preferred supplier**.
- Never automatically select a supplier from AI advice. Notes-only saves submit the currently stored supplier ID, including a retained choice outside the shortlist.
- If the saved choice leaves the shortlist, retain it and display a warning. Keep notes editing and clearing available, including with an empty shortlist. Offer only currently shortlisted suppliers as replacement options.
- Refresh shortlist options after existing supplier changes. Preserve unsaved input after failed saves; provide loading, saving, success, rejection, and retry states. Prevent duplicate submissions and discard responses belonging to an obsolete project/request or unmounted component.
- Update the workspace from the successful PUT response without refreshing or invalidating comparison advice. Display the preferred name on the workspace and dashboard; show **No Decision Yet** for null.
- Replace only the Decision placeholder. Keep existing comparison evidence and warnings visible and explain that recording a preference places no order.

Upstream changes never automatically replace or clear the preference. Decision writes change only the decision fields and ordinary project update timestamp.
