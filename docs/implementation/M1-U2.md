## Approved scope

- Add a pure, deterministic domain readiness check that returns `IN_PROGRESS`
  or `READY_FOR_REVIEW`, plus an ordered list of missing fields with one reason
  per field.
- Require non-null, non-blank `product_name`, `category`, and `destination`
  after trimming surrounding whitespace, positive `quantity`, and a valid
  `delivery_target`. Both product name and category are required. Target unit
  price is optional and does not block readiness.
- For the current cosmetic travel bag demo category, also require a `MATERIAL`
  requirement and a `CAPABILITY` requirement with `capability_key` equal to
  `CUSTOM_BRANDING`. Either `true` or `false` answers custom branding. Presence
  is independent of Requirement importance: `REQUIRED`, `PREFERRED`, and
  `INFORMATIONAL` all count as answered. Importance affects later supplier
  evaluation only.
- Match only these category labels, case-insensitively after trimming
  surrounding whitespace: `Cosmetic bag`, `Cosmetic bags`,
  `Cosmetic travel bag`, `Cosmetic travel bags`, and `Travel bags`.
  `Travel bags` is an explicit alias for the current demo category only. Do not
  use fuzzy, substring, or taxonomy matching. Other categories use only the
  core readiness checks.
- Use exactly this readiness `field_key` vocabulary and ordering when the
  corresponding information is missing:

  ```text
  product_name
  category
  quantity
  destination
  delivery_target
  requirement.material
  requirement.custom_branding
  ```

- Add an application service that recalculates and persists `IN_PROGRESS` or
  `READY_FOR_REVIEW` for unapproved briefs. It must leave `APPROVED` unchanged
  and must not perform approval.

## Explicitly out of scope

## Acceptance criteria

- An incomplete brief cannot become `READY_FOR_REVIEW`; a complete one can.
- Missing target unit price alone does not block readiness.
- The fixed demo category's material and custom-branding facts can block
  readiness, regardless of Requirement importance.
- Missing field keys and reasons are deterministic and ordered as specified.
- Recalculation updates either unapproved status in both directions while
  `APPROVED` remains unchanged.

## Implementation result

Implemented the pure deterministic readiness check and an application service
that flushes the computed status for unapproved Briefs only. The service rejects
requirements from any other project before evaluating readiness. The check returns
only the approved field keys in their fixed order, uses only the five explicit
demo category labels, and counts valid MATERIAL and typed CAPABILITY /
CUSTOM_BRANDING facts regardless of Requirement importance. No API, UI, AI,
approval transition, schema, supplier, or staleness behavior was added.

Sample briefs exercised by the tests include a complete demo brief without a
target price (`READY_FOR_REVIEW`), a demo brief missing both category-specific
facts (`IN_PROGRESS`), and a non-demo category with no demo-specific facts
(`READY_FOR_REVIEW`). Application tests verify both unapproved status
directions, initial-flush recalculation, and preservation of `APPROVED`.
