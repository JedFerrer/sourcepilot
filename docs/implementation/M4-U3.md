# M4-U3 — ComparisonSnapshot Generation and Staleness

## Status

## Objective

Persist a canonical, deterministic comparison of an approved brief, supplier facts, and current confirmed quotes. Detect changed inputs from the first snapshot, retain stale snapshots, and regenerate from current inputs.

## Dependencies and current state

## Approved scope and implementation plan

1. Add the `Comparison` persistence model and migration with `id`, `project_id`, `brief_revision`, `quote_revision_snapshot`, `comparison_payload`, `generated_at`, and `stale`. Each generation creates a new row. Retain earlier rows and expose the latest generated row as the project comparison.
2. Generate only when the brief is approved and at least two shortlisted suppliers have a current active confirmed quote. For each included supplier, use that one quote under existing quote semantics. Do not count historical or superseded confirmed quotes as additional comparison inputs. Store the active quote ID and revision for each supplier in the input snapshot so an addition, removal, replacement, or revision change is detectable, including when a newly confirmed quote is still revision zero.
3. Assemble the snapshot in a thin application service from approved requirements, curated supplier facts, current confirmed quote facts, M4-U1 source resolutions, and M4-U2 evaluator results. Preserve selected and contextual facts, quote value origins, supporting versus provenance evidence, source references, requirement importance and states, informational requirements, and typed warnings. Use stable ordering and JSON-safe values so the same authoritative state yields the same comparison payload.
4. Include deterministic, structured completeness metadata per supplier and relevant comparison field: `known` for an available selected value, `missing` for an unavailable value, and `conflicting` for unresolved same-context facts. Retain the field identity and related references. Do not calculate a score or percentage.
5. Mark stored comparisons stale when a brief revision, confirmed quote revision, or included active quote ID set changes. Add narrow staleness updates to the existing input-changing use cases, including brief edits, confirmed quote edits and confirmation, and shortlist changes. On reads, compare the stored inputs with current inputs defensively and report stale when they differ even if a write-time update was missed. A stale snapshot remains inspectable but cannot be treated as current analysis input. Regeneration creates a fresh row from current inputs; old rows remain stale.
6. Add `POST /projects/{id}/comparison/generate` and `GET /projects/{id}/comparison` with the existing anonymous-session project ownership guard. Generation rejects ineligible state without storing a partial comparison; GET distinguishes no snapshot from the latest snapshot and returns its effective stale state. Keep route handlers thin and perform generation and persistence in one transaction, using the project lock pattern already used by brief and quote writes.

## Acceptance criteria

- At least two shortlisted suppliers with current confirmed quotes are required; drafts and unshortlisted quotes never enter the payload.
- The snapshot contains current values, origins, source references, evaluator results, warnings, and structured known/missing/conflicting completeness metadata, without AI or a numeric score.
- Identical authoritative inputs produce an identical payload independent of database retrieval order.
- Brief changes, confirmed quote value changes, and active quote additions, removals, or replacements make prior snapshots stale. A read-time check catches a missed persisted stale update.
- Regeneration records latest revisions and the active quote IDs, produces a current new row, and retains stale history.
- The API isolates projects by anonymous session and does not expose another session's comparison.

## Review findings

- **P1 — shortlist approval:** Comparison generation checked Brief approval and two confirmed shortlisted quotes but did not check the existing `Project.stage == "QUOTES"` approval state. A shortlist edit moved the project back to `SUPPLIERS`, yet generation could still succeed. Generation now requires `QUOTES`. Regression coverage generates, changes the shortlist while two confirmed quotes remain, observes rejection, reapproves, and generates successfully. Existing staleness tests also reapprove after shortlist or Brief changes.
- **P2 — PDF source references:** Quote-field evidence in the comparison retained evidence IDs and extracted values but omitted its DocumentBlock link. The snapshot now includes each evidence item's stable `document_block_id`, `quote_document_id`, `page_number`, and `block_number` from the existing evidence relationship. The corrected current value, AI-extracted value, origin, evidence ID, and provenance role remain distinct. Regression coverage checks these references and confirms that full PDF block text is absent and manual values have no document evidence.
- **P2 — effective comparison currentness:** GET checked stored staleness and effective quote inputs but missed the existing approved-shortlist condition used by generation. Removing an unquoted shortlisted supplier revoked approval without changing the active quote snapshot, leaving GET incorrectly current. GET now reports effective staleness whenever `Project.stage != "QUOTES"`, while the persisted snapshot stays unchanged. Regression coverage confirms the unchanged quote map, stale GET, rejected regeneration, and return to current GET after explicit reapproval with otherwise unchanged inputs.
- **P3 — lifecycle documentation:** The implementation index still labeled M4-U3 `IMPLEMENTING`. It now matches this unit's `IN_REVIEW` status.
- Re-review confirmed the four findings are resolved, with regression coverage for the behavior changes.
