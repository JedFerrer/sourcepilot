current, reviewed shortlist of at most three project candidates.

## Dependencies and existing state

M2-U1 through M2-U6 are `COMMITTED`. The working tree was clean when planning
began. The catalog has eight stable, synthetic fixtures; deterministic retrieval
limits a category search to five candidates. Discovery persists candidates and
requirement evaluations with the Brief revision. Review already supports
selection, dismissal, notes, evidence, and stale warnings. There is no approval
endpoint or persisted shortlist approval transition. `Project.stage` currently
uses `BRIEF` and `SUPPLIERS`.

## Planned scope

1. Expand `apps/api/sourcepilot/suppliers/fixtures.json` from eight to
   approximately 15 fictional suppliers using the existing stable-ID seed
   format. Keep evidence limited to claims shown. Cover strong and near matches,
   required MOQ and material failures, missing certification, genuine conflicting
   current evidence, capability differences, and realistic lead-time and
   indicative-price tradeoffs. Preserve a useful five-candidate primary demo
   with the canonical strong, unknown, conflict, and failure examples; adjust
   fixture values or deterministic retrieval only if regression results show
   that the larger catalog displaces those examples.
2. Add a small deterministic shortlist-approval rule in the supplier domain or
   application layer. The backend will require an approved Brief, one to three
   selected, non-dismissed suppliers from this project's candidate set, and
   current evaluations against the project's Brief revision. The server will
   validate these conditions under the project lock, independent of UI state,
   and return a recoverable conflict when the selection or evaluation is not
   ready. A single selected supplier is valid; the UI will explain that
   side-by-side comparison later needs at least two.
3. Add the session-scoped `POST /projects/{id}/shortlist/approve` endpoint and
   typed response. Explicit approval advances the persisted project stage to
   `QUOTES`. Repeating approval of the same current selection should be safe.
   Any subsequent shortlist selection change, including dismissing an approved
   shortlisted supplier, returns the stage to `SUPPLIERS` so the changed set
   needs explicit approval. Restoring that supplier does not automatically
   re-approve the shortlist. A meaningful Brief edit after
   approval likewise returns the stage to `SUPPLIERS` (or existing `BRIEF` when
   readiness is lost), preserving the existing stale-evaluation and refresh
   flow. Notes and review of unselected suppliers do not revoke approval.
   Re-discovery that changes the selected set also revokes approval. Keep this
   state in the existing project and candidate records unless implementation
   reveals a concrete need for a schema change.
4. Extend the supplier review UI with a selected-supplier approval summary
   showing required and preferred statuses, important Unknown and Conflict
   states, and unresolved concerns from current evaluation/evidence data.
   Provide **Approve Shortlist** and **Continue Reviewing** actions, clear
   selected count and limit messaging, loading/error recovery, and a visible
   approved state. Refresh the project stage after approval or revocation.
   Show `Quotes` as the current stage once approved, while keeping quote entry
   unavailable until M3.
5. Keep the repository README's explicit synthetic-data disclaimer accurate;
   document the expanded catalog only if needed for demo/setup instructions.

## Acceptance criteria

- The catalog contains approximately 15 synthetic records with explicit
  fictional provenance and the required variation. Re-seeding is repeatable
  and leaves unrelated catalog rows intact.
- The primary cosmetic-travel-bag demo returns five useful candidates including
  required failure, Unknown, Conflict, and commercial tradeoffs; no numeric
  match score or fabricated evidence is shown.
- The user can approve one, two, or three current candidates. Four or more
  cannot be approved. Empty selection, dismissed selection, unapproved Brief,
  stale selected evaluation, and cross-project/session access are rejected.
- Approval is an explicit user action and advances the project to `QUOTES`.
  Changing the approved selection or meaningful Brief inputs invalidates that
  approval; stale evaluations require re-discovery/re-evaluation before a new
  approval. The UI never labels stale findings current.
- The approval summary lets the user inspect required and preferred results,
  important uncertainty and conflicts, and concerns before approving.

## Tests and evals

- Fixture regression tests for count, unique/stable IDs, synthetic notice,
  scenario coverage, seed repeatability, and primary-demo retrieval/evaluation.
- Deterministic approval-rule and API tests for counts 0–4, candidate
  membership, dismissed and stale cases, Brief state, idempotent retry,
  concurrent update/approval ordering, and session isolation.
- Integration tests for stage transitions after approval, selection change,
  Brief edit, re-discovery with changed selected candidates, and post-approval
  dismiss/restore. Verify dismissal moves `QUOTES` to `SUPPLIERS`, restoration
  leaves it there, and only explicit re-approval returns it to `QUOTES`.
- Frontend interaction tests for summary, count limit, approval/continue
  actions, errors, stale refresh, and project-stage display.
- No new model call or prompt is planned. Run the existing supplier explanation
  groundedness eval/regression tests because fixture evidence changes can
  affect them. Run backend pytest/Ruff/Pyright and frontend test/typecheck/lint.

## Risks and decisions to verify during implementation

- More category-matching fixtures can displace the carefully designed demo
  five under the current ordering. Regression tests must pin useful outcomes
  without relying on a numeric fit score or hiding informative failures.
- The existing `Project.stage` can represent the explicit approval checkpoint
  for M2. Approval invalidation must be atomic with selection and Brief edits
  so concurrent requests cannot leave `QUOTES` attached to an unapproved set.
- The approval summary must derive facts from persisted current evaluations;
  indicative prices and general lead times remain supplier context, not
  project-specific quote facts.
