## Proposed implementation

### 1. Preserve the analysis lifecycle while verifying freshness

- Keep a single in-memory analysis operation bound to project ID, snapshot ID and operation generation, with pending/result/error states. Separate its lifetime from comparison-read sequencing and freshness presentation.
- Focus and read-only refresh start verification, not cancellation. Keep the pending operation and its eventual success/error. Suppress current advice presentation while freshness is unknown; keep a visible pending or verification message and prevent a second analysis submission.
- Reconcile an authoritative same-ID, non-stale response by retaining pending, result or error. Results arriving during verification remain held until the latest applicable read verifies the binding. A failed verification shows a recoverable read error and a GET-only retry, retaining the terminal outcome internally; it must not silently discard it or automatically rerun AI.
- Invalidate immediately for explicit regeneration, project change or unmount. Invalidate on authoritative missing/replaced/stale comparison or changed eligibility/scope. Known upstream writes suppress current presentation immediately; their follow-up read decides whether the actual comparison remains valid. Never infer freshness from object equality or preferred-supplier/name changes.
- Use one ordered reconciliation path for focus reads and the post-analysis verification read. A slower old read cannot restore current status after newer stale evidence. Retain backend freshness checks and do not let a late response from project A update project B, including A→B→A navigation.
- Display a terminal error until an explicit retry or actual invalidation. Retain settled-success behavior and successful null suggestion. Full browser reload/navigation recovery is excluded: advice is not persisted.

### Why a local timeout patch is insufficient

Source inspection in this correction turn identified another executor path: HTTPcore's AnyIO transport calls `anyio.connect_tcp`; AnyIO's asyncio backend resolves hostnames through `loop.getaddrinfo`; Python 3.11 implements that call using the default executor. Psycopg's asynchronous hostname resolution also uses `loop.getaddrinfo` when a hostname requires resolution. Therefore bypassing only SDK platform detection does not establish bounded request-local Runner shutdown. These additional paths were inspected in installed source, not reproduced against external DNS or a provider in this turn.

Moving to a persistent event loop, abandoning executor shutdown, or returning while helper threads continue would hide continuing work rather than establish the requested bound. No such change is authorized or implemented. Running platform detection before the timer would also exclude request preparation from the stated guarantee.

There is a separate guarantee conflict at total exhaustion: once the entire wall-clock allowance has elapsed, positive-duration awaited cleanup cannot both receive new time and remain inside that same allowance. Independent attempts must normally have protected time reserved before the total, with an explicit forced-release/unsuccessful-cleanup policy for overruns. Successful graceful cleanup and trace persistence cannot be promised after arbitrary non-cooperative stalls.

### Decision and the guarantee that cannot be met

**Recommend using the existing FastAPI/Uvicorn application event loop, one request-owned async session/provider client, and an explicit cooperative execution deadline. Do not introduce a per-request process for this defect. This recommendation requires approval of a changed guarantee, not just an implementation detail.**

The original unconditional interpretation—return by exactly the total deadline, stop every local helper, finish independent awaited cleanup even if the total is already exhausted, prevent every possible late database commit, and guarantee response delivery—cannot be met by either evaluated approach with the present stack and constraints. Python cannot interrupt a running OS resolver thread; synchronous work can block its event loop; process startup/termination/reaping is not a hard-real-time primitive; database commit acknowledgement can be lost; client receipt is outside the backend's control. No experiment establishes those guarantees.

The proposed replacement is an absolute **application work/advice-acceptance cutoff** plus reserved, independent cleanup attempts and a measured response-handling target for cancellation-cooperative operations. A late result is never accepted. No new model, tool, repair or database write is started after its applicable cutoff. However, already-running OS helpers and a remotely accepted trace transaction may finish later. Non-cooperative work can also delay local response or application shutdown. These are explicit exceptions, not successful deadline enforcement. If the user requires zero surviving local work at the original deadline, reject this recommendation and keep implementation blocked pending a broader architecture decision.

### Recommended lifecycle and budget, conditional on approval

1. **One application loop.** Make only the comparison HTTP orchestration awaitable. Reuse `AsyncSession.run_sync` for existing bounded synchronous database/application functions where appropriate; keep all database waits and the async SDK on the same task. Remove request-owned Runner use in HTTP handling. CLI/eval entry points use one top-level lifecycle for the invocation, not one Runner per analysis; their process shutdown is separately reported and may wait for helpers. Do not silently leave synchronous direct entry points claiming the stronger deadline.
2. **Start boundary.** Capture a monotonic timestamp when the matching request first enters application handling, before body consumption, dependency acquisition, authorization and comparison preparation. Admission, body reading, validation, initialization, connection acquisition, retries/backoff, repair, final freshness verification, result serialization and response-send attempts consume that original budget. No retry resets it. Time before the ASGI application receives the request and application process startup before accepting traffic are outside the per-request budget. Cold work performed after receipt is inside it. Preloading required modules at application startup may reduce cold delays, but is not evidence of a hard request bound.
3. **Default schedule for approval.** Retain 180 seconds total target and 60-second shrinking provider-attempt cap. Stop ordinary execution by `start + 175s`. Reserve the final five seconds explicitly: up to one second for cancelling active I/O and closing provider resources, one second for rollback/session closure, half a second for engine disposal, one and a half seconds for terminal trace persistence and its own closure, and one second for response preparation/ASGI send attempt. Early completion uses at most the same five-second cleanup allowance, clamped to the original end. Successful cleanup does not automatically wait for the entire reserve. Per-resource sublimits must be tested; they are proposed allocations, not measured guarantees.
4. **Independent cleanup.** Each resource gets its own bounded attempt even if an earlier attempt fails or is cancelled. Preserve the primary timeout/error and record safe cleanup outcome metadata separately. Do not allow `begin_cleanup()` to throw before entering all relevant cleanup guards. If no time remains, perform only non-awaiting force-release actions verified safe for the installed driver, mark graceful cleanup incomplete and never extend ordinary execution. A zero-time callback entry is not described as successful closure. If a driver cannot be safely released, retain ownership/admission capacity and report degraded state until it actually releases; do not return a potentially active connection to a reusable pool. Do not spawn unowned cleanup tasks.
5. **Response boundary.** Prepare and size-check the result before accepting it, check time/freshness before committing to a success response, and suppress success once its acceptance cutoff passes. If enough response reserve remains, send the fixed timeout envelope. After HTTP headers are sent, an interrupted body cannot be replaced by a new JSON error; abort delivery instead. Backend timing covers its attempted ASGI handoff, not guaranteed proxy/browser receipt. Existing 190/195-second proxy/browser waits remain independently protective; they do not prove backend cancellation.

### Resource, transaction and trace ownership

- Each comparison request owns its `AsyncSession`, provider client and request-local async engine (initially keep NullPool to avoid introducing pooled-connection recovery semantics). They are never shared with another request or used concurrently. The session dependency for other operations remains unchanged. No ORM session/object is passed to resolver threads; resolver helpers receive only connection metadata. Cancellation must be checked before/after synchronous sections and before every new I/O/commit boundary.
- No comparison code writes business facts or advice. This preserves confirmed quotes, comparison snapshots and human preferences even if analysis fails. Intermediate and terminal AIRun metadata remain the only analysis writes. Result data is response-only; a cancelled request has no callback that can publish a later result or resume tools/repair.
- After a database failure, rollback must precede any freshness query. If rollback fails or the connection is invalidated, discard that connection; use a fresh, request-owned session for bounded verification/terminal tracing if its allotted time remains. Never query through a failed transaction. Use short PostgreSQL statement/lock waits clamped to remaining stage time; do not claim client socket closure immediately stops server execution.
- Capture safe run ID, counters, usage, intended outcome and committed step sequence before recovery. Terminal persistence has one owner, uses actual committed sequence state and idempotent terminal-state rules, and cannot race a background finalizer. No trace-writing task survives the request. Do not start a terminal write after its subdeadline; if persistence cannot be confirmed, report that limitation instead of claiming TIMED_OUT was durably recorded. A previously sent commit can still succeed after local cancellation: neither process termination nor a timer can retract it. This uncertainty is limited to trace metadata, not supplier decisions or persisted advice.
- Optional tracing must remain metadata-only and best-effort. Synchronous SDK initialization/export hooks cannot be promoted to hard-bounded operations by surrounding them with an async timeout. Test enabled, disabled and unavailable tracing; if an optional hook stalls, the request may miss the cooperative timing target. Do not add detached exporter work to conceal that limitation or change optional observation classification in this correction.

### Concurrency, platform and shutdown implications

- **Admission and helper accounting:** propose a fixed small cap (two active-or-draining comparison requests per API worker, no waiting queue). A request retaining unresolved resources/helper futures retains its slot, even after its HTTP response ends. Reject further comparison attempts with a recoverable capacity error; never start paid work while waiting for a slot. This bounds accumulation but can make comparison unavailable until the host resolver recovers or the application is restarted. Multi-worker deployments multiply the cap; no cross-tab/global deduplication is added.
- A narrowly instrumented application-owned default executor can associate submitted futures with the current comparison owner, track the underlying future until actual completion and release the retained slot on the event loop. Preserve executor behavior for other operations. The experiment proves cancelled DNS wrappers do not lose underlying-future accounting; production integration must additionally prove SDK and DB resolver coverage, no false release, shutdown behavior and no unrelated-operation regression. Do not implement a general job framework. If that cannot be achieved narrowly, stop rather than discard accounting. Reject/fail closed on an unexpected comparison helper that can perform model or database writes; the installed psycopg nonblocking cancellation capability must be verified instead of assuming its older thread-based cancellation fallback is safe.
- **Windows:** current installed Uvicorn uses Proactor in the ordinary non-reload case; psycopg async explicitly rejects it. Reload/worker settings affect Uvicorn's factory. The application-loop option therefore requires a supported explicit Selector-loop launcher/configuration for ordinary, reload and E2E startup. Validate all entry points, not just `--reload`. Do not create a private loop to hide this mismatch. Installed versions inspected: Python 3.11.9, psycopg 3.3.6, libpq 18.4. Versions on another host may differ.
- **Linux/other hosts:** use the supported asyncio event loop with the existing driver. POSIX source compatibility is not test evidence. Require Linux verification before claiming deployment portability; macOS is not separately certified by these experiments. Do not assume uvloop behavior matches the tested default-executor integration.
- **Application shutdown:** stop admission, cancel active comparison tasks and attempt owned cleanup within the lesser of request remaining time and the server's shutdown allowance. Retain accounting until tasks/helpers finish. Python may still wait for a blocked executor thread on final shutdown; ordinary application code cannot promise a bounded process exit. No new supervisor is introduced. An operator-forced application termination loses trace/cleanup guarantees and is an explicit failure mode, not a successful request cancellation.
- **Browser disconnect:** preserve the approved behavior that disconnect may leave the existing request running up to its work cutoff. If ASGI cancellation is delivered, propagate it and clean up without starting more work. Do not claim that browser abort, proxy timeout or local provider closure cancels remote provider processing/billing. A socket close does not create a durable result or a retry. Preserve the existing mounted-page retry cooldown.

### Why the process alternative is not the recommendation

A process could own the entire analyst/session/provider lifecycle, with a parent owning admission and a bounded IPC protocol. Startup, imports, IPC, work, graceful cleanup, forced termination, reaping and parent response handling would all need reserved time. Successful output could be accepted only after final freshness validation and child exit; killing a child loses its Python cleanup/final trace. Giving the parent a separate terminal-write session adds a second database lifecycle, and uncertain child commits require idempotent handoff rules.

The finite Windows trial supports stopping blocked helpers, but plain processes fail the parent-crash requirement. Windows kill-on-close Job Objects and an explicitly tested POSIX parent-death/process-group strategy would need assessment; neither is implemented or validated here. Python daemon-process shutdown is not a parent-crash guarantee. Forced termination does not cancel a remote provider or retract an accepted database commit. Process creation/reaping can also exceed a timer under host failure. These concerns turn the proposal into an execution-supervision subsystem, disproportionate to this defect unless strict local containment becomes a separately approved architecture requirement. It should not be smuggled into V1 as a small timeout fix.
