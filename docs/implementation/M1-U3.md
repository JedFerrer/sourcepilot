## Approved scope

- A strict `ExtractedBrief` contract with nullable core fields, explicit bounded `attributes[]`, explicit bounded `requirements[]`, and ambiguities. Reuse existing domain value validators. Unstated values and requirement importance remain absent/unknown.
- `brief-interpreter-v1` prompt, project-scoped application service, structured model call, deterministic validation, and AIRun recording.
- A minimal correction to the shared structured-call helper so one provider retry and one schema-repair retry have independent operation-wide budgets. At most three invocations occur in a mixed-failure operation.
- Deterministic automated eval fixtures and an opt-in live-model eval command using existing AI/AIRun infrastructure.
- Recoverable failure that preserves project access, `original_request`, and any existing Brief.

## Retry conflict and approved resolution

The M0-U5 unit document approved a global cap of two provider invocations. That cap prevents the Technical Architecture's provider retry and schema-repair guarantees from both applying when one operation encounters both kinds of failure. The Technical Architecture has higher authority. The human explicitly approved independent, single-use budgets for M1-U3: one retryable provider-failure retry and one invalid-output repair retry after the initial invocation. This permits three invocations only in a mixed-failure path. No other M0-U5 cleanup or redesign is approved.

## Approved implementation plan

1. Define `ExtractedBrief`, bounded attributes and requirements, and `brief-interpreter-v1`. Validate extracted values through the existing Brief/Requirement domain validators; never infer unstated facts or importance.
2. Add a project-scoped interpreter that reads `original_request`, uses the structured-call helper, and returns the validated extraction and AIRun without writing Brief fields or calculating readiness.
3. Correct only shared-helper retry accounting. Keep one AIRun; `attempts` is the actual provider invocation count, and existing status/validation/error fields describe the outcome.
4. Add mocked contract and failure tests, project preservation/API regression coverage, 12 deterministic eval fixtures, and an opt-in live eval command without a new framework.
5. Run backend tests, deterministic eval tests, Ruff, and Pyright. Record Browser QA as not applicable, then stop before Review without committing.

## Acceptance criteria

- A valid request produces a bounded `ExtractedBrief` with separate `attributes[]` and `requirements[]`.
- Missing facts and unstated importance remain unknown/absent; invalid domain values are rejected.
- Each retry budget is consumed at most once; both approved three-invocation mixed-failure paths work and exhaustion is terminal.
- AI failure leaves the project retrievable and its original request and existing Brief unchanged.
- AIRun records project, model, prompt version, input hash, actual attempts, outcome, latency, and available tokens using the existing schema.
- Initial deterministic evals run; live evals are opt-in only.

## Tests and evals

- Contract and mocked-model tests for valid/invalid output, bounded attributes/requirements, unknowns, importance, ambiguity, and recovery.
- Retry tests: provider failure → retry → invalid → repair success; invalid → repair provider failure → provider retry success; provider failure → retry provider failure → terminal provider failure; invalid → repair invalid → terminal validation failure.
- Existing-project API regression after interpreter failure, with unchanged `original_request` and Brief.
- Twelve version-controlled brief cases with deterministic scoring; opt-in live-model evaluation.
- Backend pytest, Ruff, and Pyright.

## Review findings

Two approved findings were addressed on 2026-09-23 for re-review:

1. `ExtractedBrief` now uses strict integer fields for core quantity, MOQ/QUANTITY values, and production lead time. The capability value union is also strict, so Pydantic cannot convert numeric input into a boolean before the existing domain validator checks it. Regression tests reject string and boolean integer inputs and numeric capability input.
2. Brief eval scoring now checks all nine extraction fields by default, treating omitted expected values as null or empty lists. A fixture must explicitly opt into partial scoring. The `missing-quantity` fixture now expects no requirements, and its offline output no longer contains the hallucinated material requirement. Regression tests show that extra requirements, attributes, and core values fail. A failed live-model result scores zero while its case remains in the denominator and the AIRun failure is reported. The live command remains manual and opt-in; CI behavior is unchanged.
