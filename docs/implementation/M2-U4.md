## Approved implementation plan

1. Add `ProjectSupplier` with notes, shortlist/dismissal state, and `evaluated_against_brief_revision`; add `RequirementEvaluation` only for results tied to persisted Brief requirements. Derived MOQ context has no persisted evaluation row.
2. Discovery saves candidates and evaluations atomically. Re-discovery preserves review state for returning suppliers and removes disappeared candidates, including their notes, shortlist/dismissal state, and evaluations. This removal is intentional; a later reappearance starts with fresh review state.
3. Derive stale state by comparing each ProjectSupplier revision to Project.brief_revision. Stale results remain inspectable as historical candidate context but are not presented as current requirement findings. Refresh uses the existing Brief approval semantics.
4. Add session-scoped supplier listing and review updates. Expose catalog evidence and requirement findings without a numeric score or AI explanation.
5. Add project-workspace supplier review UI with discovery/refresh, evidence, requirement states, notes, shortlist toggle, dismiss/restore, and stale warnings.

## Explicitly out of scope

Shortlist approval and the three-supplier approval limit (M2-U7), analyst tools/explanations (M2-U5/U6), new Brief approval behavior, live research, and new dependencies.

## Acceptance criteria

- Evaluations and candidate revision persist; stale state follows the ProjectSupplier revision.
- Derived context is separate from requirement-linked rows.
- Re-discovery behavior for returning and disappeared candidates matches the plan.
- Review actions work while results are stale, and stale findings are never labeled current.
- Session ownership is enforced on every API operation.

## Review findings and fixes

The approved review findings were fixed on 2026-09-25:

1. **Backend stale-state race:** Supplier listing now locks and refreshes the
   current Project before reading its Brief, requirements, and evaluations in
   the same transaction. The review update also refreshes the Project when it
   acquires its write lock. Regression tests load the old Project, commit a
   Brief edit in another session, then verify listing and review updates report
   the new revision with old evaluations marked stale and hidden.
2. **Frontend out-of-order requests:** Supplier reloads now apply only the
   latest request result. A regression test resolves the newer response first
   and verifies an older response cannot replace its supplier state or stale
   warning.
3. **Frontend Brief-change reload failure:** Displayed supplier findings are
   tied to the project and Brief refresh that loaded them. A Brief-triggered
   refresh immediately suppresses the prior requirement findings, including
   while the reload is pending and after a failed reload. A regression test
   covers current findings, a Brief-triggered reload, and a network failure.
