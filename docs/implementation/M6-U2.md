## Implementation steps

### 1. Define the narrow internal tracing boundary

- Represent run identity, operation, model, prompt version, timestamps, latency, attempts, validation, terminal status, normalized failure category, token usage and Analyst counts/configured limits.
- Extend the existing boundary only as needed for sanitized lifecycle observations; do not create a generic event system.
- Export only explicitly allowed metadata. Keep session identifiers local. Exclude cookies, session tokens, credentials, raw requests, prompts, model output, PDF text, tool arguments/results and exception messages.
- Restrict exported tool names and error categories to known values; map unrecognized values to safe labels. Preserve public response contracts and model-provider interfaces.

### 2. Complete application-owned observability

- Extend existing ordered step recording to structured operations, preserving historical data and Analyst event ordering.
- Record applicable model attempts, provider retries, schema/semantic repair, validation outcomes and terminal success/failure. Preserve timeout/provider, tool, limit, scope and processing-failure distinctions available at the existing boundaries.
- Sum reported tokens across attempts instead of retaining only the final structured response. Preserve unknown usage and identify partial totals rather than presenting them as complete.
- Keep `estimated_cost` nullable. Do not introduce pricing tables or treat missing cost as zero.
- Persist final AIRun metadata before optional terminal export on normal and exceptional paths. Preserve original exceptions, transaction boundaries, stale-processing write guards and existing recovery behavior; optional tracing must not mask persistence failures.
- Preserve existing Analyst tool-count semantics, configurable four-turn/six-tool defaults, retry/repair limits, scope checks, prompts, contracts and validators.
- Continue using quote-processing failure records for failures before AIRun creation. This unit does not add crash-recovery infrastructure or redesign abandoned-work recovery.

### 3. Connect optional Langfuse tracing

- Add a lazily initialized process-scoped SDK adapter behind the no-op boundary. Declare a bounded compatible optional extra and resolve it through the existing lockfile during separately authorized implementation.
- Require explicit enablement and server-side configuration. Disabled tracing must not import the optional SDK or initiate network activity.
- Create one root observation per AIRun correlated by run ID, with ordered model/tool observations and retry, validation, limit and terminal events.
- Attribute token usage once at the appropriate observation level to avoid double counting; omit unavailable costs. Do not manufacture per-attempt measurements absent from the provider.
- Use SDK background delivery with bounded transport settings. No per-request flush, application export-retry loop, durable export queue or custom ingestion client.
- Isolate initialization, recording, export and shutdown failures. Missing configuration/package or unavailable Langfuse produces sanitized diagnostics and falls back to application-owned observability without changing business results.
- Close observations on success and failure; wire bounded shutdown handling for API and existing short-lived execution paths.
- Use documented manual observation APIs, not automatic decorators/wrappers that capture inputs or outputs. Reference: https://langfuse.com/docs/observability/sdk/overview and https://langfuse.com/docs/observability/sdk/instrumentation.

### 4. Document inspection and evidence

- Document optional installation/configuration, disabled behavior, run-ID correlation, local record inspection, SDK lifecycle and outage limitations.
- Demonstrate Brief, Quote and Analyst traces using existing deterministic fixtures and test entry points.
- Record latency and available token/cost summaries by operation from identified evidence, with sample counts, models, prompt versions, failures and missing values. Separate deterministic timings from retained live measurements.
- Reuse M6-U1 evidence read-only. Do not rerun paid live baselines, rewrite historical reports or introduce a new reporting/verification framework.
- Limit changes to backend tracing/runtime hooks, existing test infrastructure, optional dependency/configuration declarations, focused documentation and unit/index records. Any CI adjustment must remain within existing jobs and be necessary to test optional/disabled behavior.
