## Approved scope

- Add a non-null `projects.brief_revision` integer with server/default value
  `0` and an explicit increment helper. Automatic meaningful-edit rules and
  stale detection remain later-unit work.
- Add one cascade-deleted `Brief` per `Project` with:
  - non-null UUID `project_id` primary/foreign key;
  - nullable bounded-text `product_name`, `category`, and `destination`;
  - nullable positive-integer `quantity`;
  - nullable JSONB `delivery_target` validated as one of the bounded shapes
    below;
  - nullable fixed-precision `Numeric(12,4)` `target_unit_price`, never a
    floating-point value;
  - non-null `IN_PROGRESS`, `READY_FOR_REVIEW`, or `APPROVED` status; and
  - nullable timezone-aware `approved_at`.
- Add cascade-deleted project-owned `Requirement` records with UUID identity,
  `project_id`, explicit `kind`, explicit `importance`, validated JSON
  `expected_value`, and nullable notes.
- Persist the approved V1 mappings:
  - Brief fields hold product name/category, requested quantity, destination,
    delivery target, and target unit price.
  - `MATERIAL` holds material; `CERTIFICATION` holds certification; `MOQ`
    holds acceptable MOQ.
  - `CAPABILITY` holds custom branding, branding method, product features,
    supported category, or manufacturing capability.
  - `QUANTITY`, `UNIT_PRICE`, `PRODUCTION_LEAD_TIME`, and `DELIVERY` persist
    future explicit comparison constraints required by the approved M2/M4
    evaluator roadmap; their business rules are not implemented here.
  - `INFORMATIONAL` holds dimensions, size/capacity, color, packaging,
    labeling, product-description context, branding notes, and other
    non-evaluable context.
- Limit the persisted requirement-kind vocabulary to `MATERIAL`,
  `CERTIFICATION`, `MOQ`, `QUANTITY`, `UNIT_PRICE`,
  `PRODUCTION_LEAD_TIME`, `DELIVERY`, `CAPABILITY`, and `INFORMATIONAL`.

## Bounded validated value shapes

- `CAPABILITY.capability_key` is exactly one of `PRODUCT_CATEGORY`,
  `CUSTOM_BRANDING`, `BRANDING_METHOD`, `PRODUCT_FEATURE`, or
  `MANUFACTURING_CAPABILITY`; its payload is the key plus either a boolean or
  normalized non-empty categorical value appropriate to that key.
- `INFORMATIONAL.subject` is exactly one of `DIMENSIONS`,
  `SIZE_OR_CAPACITY`, `COLOR`, `PACKAGING`, `LABELING`, `PRODUCT_DESCRIPTION`,
  `BRANDING_NOTES`, or `OTHER_CONTEXT`; its payload is the subject plus
  non-empty free text.
- `delivery_target` is exactly one of:
  - date: `{"kind": "DATE", "date": "YYYY-MM-DD"}`;
  - period: `{"kind": "PERIOD", "label": "<non-empty text>", "start_date": "YYYY-MM-DD" | null, "end_date": "YYYY-MM-DD" | null}`.

  A period may use its label alone when no calendar bound is known; later
  evaluators treat insufficiently bounded timing as unknown rather than infer
  a date.
- `expected_value` is only validated storage for explicit per-kind shapes:
  normalized non-empty text for material/certification; positive integers for
  MOQ/quantity; a lossless decimal string plus optional ISO currency for unit
  price; positive integer days for production lead time; one bounded delivery
  shape for delivery; and the bounded capability/informational shapes above.
- JSON must not contain arbitrary keys, dynamic field paths, operators,
  formulas, predicates, or executable rules.

## Explicitly out of scope

- Supplier fixtures, retrieval, requirement evaluation, supplier staleness,

  FX conversion, or any unapproved dependency or infrastructure.

## Review findings

The valid M1-U1 review findings were addressed on 2026-09-23:

- `target_unit_price` now rejects non-Decimal, non-positive, non-finite,
  excess-scale, and excess-magnitude values before `Numeric(12,4)` storage.
  Boundary tests verify lossless database round trips for `0.0001` and
  `99999999.9999`, plus rejection of excess scale and magnitude.
- Focused tests now cover the `projects.brief_revision` and `Brief.status`
  defaults, the one-Brief-per-Project constraint, extra JSON keys for Brief
  delivery and Requirement values, and float price rejection independently
  of quantity validation.
- JSON-validation bypass investigation: the supported application write paths
  in `sourcepilot` create DemoSession, Project, and AIRun records only. No
  supported Brief or Requirement bulk/Core/direct-SQL write path exists in
  the repository. Their current ORM persistence uses `before_insert` and
  `before_update` validators. Arbitrary direct SQL could bypass those hooks,
  but is not a supported SourcePilot application path; this finding is
  non-blocking and requires no change.

The review findings are resolved. Browser QA is not applicable for this
internal-only unit.
