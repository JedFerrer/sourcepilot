## Objective

Create the persistent supplier catalog and approximately eight fictional supplier
fixtures needed by later candidate retrieval. Make their capabilities and
supporting or contradictory evidence inspectable through backend repository
queries.

## Planned scope

1. Add `Supplier`, `SupplierCapability`, and `SupplierEvidence` SQLAlchemy
   models and one reviewed Alembic migration. Suppliers are global curated
   catalog records, not project or demo-session records. Use stable UUIDs,
   required name/country/description, and nullable general MOQ, general lead
   time, and indicative price. Keep commercial values typed, positive where
   present, and currency explicit for any indicative price.
2. Give capabilities a supplier foreign key, explicit kind, and normalized
   value. Cover category, material, certification, and relevant manufacturing
   or branding capabilities with a bounded vocabulary compatible with the
   existing Brief requirement kinds. Give evidence its own ID, supplier foreign
   key, claim key, source type/label, optional source reference, evidence text,
   and evidence state. Preserve separate records for incompatible claims about
   the same fact and context. Missing evidence stays missing; it does not become
   negative evidence. Add only the constraints and indexes needed for integrity
   and supplier/claim lookup.
3. Add a focused supplier repository that can list suppliers in stable order
   and fetch a supplier with its capabilities and evidence. Keep it read-only
   for application callers; seeding owns fixture writes. Do not add candidate
   ranking or filtering yet.
4. Add approximately eight explicitly fictional suppliers centered on the
   cosmetic travel bag demo scenario. Include a strong match, a useful near
   match, a required MOQ failure, an unknown certification or capability, and
   two incompatible current synthetic certification records for one supplier.
   Vary category, material, branding, MOQ, lead time, and indicative commercial
   information enough for later structured retrieval and evaluation. Keep
   evidence small and tied to claims the product will show.
5. Add an explicit, repeatable seed command. Store fixture content and stable
   identifiers in version control. Upsert only the managed fixture records and
   their child records in a transaction, so a second run produces the same
   catalog without duplicates or random IDs. Never seed automatically at API
   startup or erase unrelated data.
6. Add a root README statement that supplier names, capabilities, evidence,
   and eventual quote fixtures are synthetic and make no claims about real
   manufacturers. Document the migration, seed, and catalog inspection commands
   in local development instructions.

## Acceptance criteria

- A clean migration creates exactly the three supplier tables with the planned
  relationships and constraints; downgrade removes only this unit's schema.
- The explicit seed command loads approximately eight fictional suppliers.
  Running it twice preserves the same IDs, supplier count, capabilities, and
  evidence without duplicate rows.
- Repository queries return suppliers, capabilities, and evidence consistently,
  including the genuine same-context conflict and absent evidence for an
  unknown case.
- Fixture data supports the five required example categories: strong match,
  near match, required failure, unknown, and genuine conflict. It does not use
  real manufacturer names or imply real-world verification.
- The README clearly labels all supplier and future quote fixtures as synthetic.
  The demo checkpoint can inspect seeded supplier and evidence records.

## Tests and evals

- Fixture tests assert count, stable IDs, repeatable seed, intended scenario
  coverage, fictional labeling, and no duplicate children after reseeding.
- Repository tests assert stable ordering, capability/evidence retrieval,
  supplier isolation, missing evidence, and both sides of the conflicting
  certification claim.
- Migration tests assert tables, keys, constraints, upgrade/downgrade behavior,
  and preservation of pre-existing non-supplier data.
- Run relevant backend pytest tests, Ruff, Pyright, Alembic checks, and the
  repository's applicable type/lint checks. No AI eval applies to this unit.

## Risks and decisions to verify during implementation

- General supplier prices need an explicit currency and must remain indicative;
  they are not project quotes. General lead time must not be treated as a
  project-specific promise.
- The architecture describes approximately 15 records for the complete V1
  catalog; M2-U1 explicitly starts with approximately eight and M2-U7 completes
  the fixture set. This is a staged count, not a change to the V1 target.
- A genuine conflict requires opposing claims about the same current fact in
  the same context. Two different contexts or a missing record do not qualify.
