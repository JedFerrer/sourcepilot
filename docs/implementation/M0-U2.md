## Approved implementation plan

1. Add SQLAlchemy, Alembic, and `psycopg` to the API dependencies and regenerate the locked dependency file.
2. Add a database module that reads `DATABASE_URL` for normal application persistence, creates the synchronous SQLAlchemy engine and session factory, and exposes a per-operation session dependency. `TEST_DATABASE_URL` is required only by persistence/integration tests and CI; it must not be required for normal application startup or runtime.
3. Add typed SQLAlchemy declarative models and shared metadata for only the initial tables:
   - `DemoSession`: UUID primary key; unique, indexed `opaque_token`; `created_at`, `last_seen_at`, and `expires_at`.
   - `Project`: UUID primary key; required `demo_session_id` foreign key to `DemoSession` with database cascade deletion; `name`; `original_request`; `stage` defaulting to `BRIEF`; `created_at`; and `updated_at`.
4. Initialize Alembic and create one reviewed initial revision that creates only `demo_sessions` and `projects`, with their foreign-key, uniqueness, and lookup indexes. Document `upgrade head`, `current`, and the future migration generation/review process.
5. Provide a dedicated local test database and test fixtures that reset it through Alembic. Before any reset or migration, test setup must reject a missing `TEST_DATABASE_URL` and reject a `TEST_DATABASE_URL` that targets the same PostgreSQL database as `DATABASE_URL`; do not rely on a hard-coded database-name check.
6. Update local-development instructions and CI so CI starts the approved Compose PostgreSQL service, waits for readiness, supplies `TEST_DATABASE_URL` only to the persistence test path, and runs the backend checks against the isolated test database.

## Review findings

- P2 resolved on 2026-09-22: `DemoSession.opaque_token` combined a unique constraint with a separate non-unique lookup index, although PostgreSQL already creates an index to enforce the unique constraint. The ORM model now declares only `unique=True`, and the uncommitted initial `0001_persistence_foundation` migration now creates only its `opaque_token` unique constraint; no follow-up migration was added. The migration smoke test asserts that exactly one uniqueness constraint covers `opaque_token`.
- P2 resolved on 2026-09-22: The migration smoke test verified only the resulting tables after its Alembic reset/upgrade, so it did not prove that the database was at the intended migration revision. It now asserts that `alembic_version` contains exactly `0001_persistence_foundation`, while retaining the existing application-table and schema-boundary assertions.
- P1 resolved on 2026-09-22: IPv4-mapped IPv6 resolved addresses (for example, `::ffff:127.0.0.1`) were not canonicalized through their mapped IPv4 address before loopback classification, allowing the same-database test safety guard to distinguish them from `127.0.0.1`. The safety check now maps IPv4-mapped IPv6 addresses to IPv4 before collapsing loopback identities. Focused coverage rejects the mapped-loopback/IPv4 equivalent case while retaining the existing `localhost`, `::1`, `127.0.0.1`, distinct-database, and genuinely different non-loopback target coverage.
- P1 resolved on 2026-09-21: `alembic.ini` supplied an effective hard-coded database URL, allowing command-line migration commands to ignore the documented `DATABASE_URL` configuration. Alembic now requires `DATABASE_URL` for normal migration commands while retaining the explicit programmatic test override used for the isolated test database; focused coverage verifies the missing-variable error.
- P1 resolved on 2026-09-21: CI performed only a one-shot PostgreSQL readiness probe after starting Compose. CI now waits for the configured Compose healthcheck for up to 60 seconds and prints service status and PostgreSQL logs before failing if readiness is not reached.
